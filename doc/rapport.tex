\section{Introduction}

Ce projet a pour objectif la conception et l'implémentation d'un service web REST complet dédié à la gestion, la validation et la restitution de transactions de prélèvement bancaire SEPA, basées sur la norme internationale \textbf{ISO 20022} (\texttt{pain.008.001.02}).

Le service permet l'ingestion de messages XML, leur validation stricte selon un schéma XML Schema (XSD), leur stockage persistant dans une base relationnelle, leur recherche multicritères, ainsi que leur restitution sous forme de flux XML structurés ou de vues HTML conviviales transformées par feuilles de style XSLT 3.0.

L'application a été entièrement conçue selon les principes de \textbf{Clean Code} (\textbf{SOLID} et \textbf{DRY}) et s'accompagne d'une infrastructure moderne et autonome basée sur \textbf{Docker}, \textbf{Docker Compose} et un pipeline d'Intégration Continue (\textbf{GitHub Actions}).

    \end{itemize}

\section{Architecture Logicielle \& Principes de Conception}

L'architecture du projet repose sur un découpage en couches étanches, complété par des services spécialisés à responsabilité unique.

\subsection{Application des Principes SOLID}

\begin{itemize}[leftmargin=*]
    \item \textbf{Single Responsibility Principle (SRP) :} 
    La logique XML n'est pas mélangée à la persistance ni aux contrôleurs. 
    \begin{itemize}
        \item \texttt{XmlValidationService} est l'unique responsable de la validation XSD.
        \item \texttt{XmlSerializationService} est l'unique responsable de la conversion bidirectionnelle JAXB.
        \item \texttt{XsltTransformationService} est dédié aux transformations XSLT vers HTML.
        \item \texttt{EndpointDocumentationService} encapsule les métadonnées de documentation de l'API.
        \item \texttt{SepaApiController} traite exclusivement les flux de données REST (XML), tandis que \texttt{SepaWebController} pilote l'interface utilisateur web (HTML Thymeleaf).
    \end{itemize}

    \item \textbf{Open/Closed Principle (OCP) \& Liskov Substitution (LSP) :}
    Tous les services clés sont définis à travers des interfaces Java. Les implémentations peuvent évoluer ou être substituées sans impacter les contrôleurs ou les consommateurs métier.

    \item \textbf{Interface Segregation Principle (ISP) :}
    Les interfaces de service sont granulaires et ciblées, évitant aux clients de dépendre de méthodes superflues.

    \item \textbf{Dependency Inversion Principle (DIP) :}
    L'injection par champ (\texttt{@Autowired} sur attributs privés) a été bannie au profit exclusif de \textbf{l'injection par constructeur} avec des attributs \texttt{final}. Cela garantit l'immutabilité des composants et facilite grandement l'isolation lors des tests unitaires sans nécessiter de contexte Spring complexe.
\end{itemize}

\subsection{Application du Principe DRY (Don't Repeat Yourself)}

\begin{itemize}[leftmargin=*]
    \item \textbf{Mise en cache des ressources lourdes :} L'instance de schéma XSD (\texttt{Schema}) et le contexte JAXB (\texttt{JAXBContext}) sont pré-instanciés une seule fois au démarrage de l'application, évitant de recharger et parser les schémas à chaque requête HTTP.
    \item \textbf{Templating modulaire Thymeleaf :} La barre de navigation et le pied de page sont factorisés dans un composant unique (\texttt{fragments/layout.html}) et réutilisés dans toutes les pages de l'application.
    \item \textbf{Centralisation CSS :} Tous les styles de l'application sont centralisés dans \texttt{sepa26.css} avec des variables CSS, évitant toute duplication de règles CSS inlinées.
    \item \textbf{Génération uniforme des erreurs :} Un formatage réutilisable des messages d'erreur évite l'éparpillement de chaînes XML codées en dur.
\end{itemize}

\subsection{Stack Technique}

\begin{itemize}
    \item \textbf{Langage :} Java 25 (LTS).
    \item \textbf{Framework :} Spring Boot 4.1.1 (Spring Web, Spring Data JPA).
    \item \textbf{Gestion des dépendances \& Build :} Apache Maven.
    \item \textbf{Base de données :} MariaDB 11 en production / Docker, et H2 Database en mémoire pour l'exécution des tests.
    \item \textbf{Traitement XML :} Jakarta XML Binding (JAXB 4.0), Saxon-HE 12.9 (moteur XSLT 3.0), Jackson XML.
    \item \textbf{Moteur de rendu Web :} Thymeleaf.
    \item \textbf{Conteneurisation \& CI :} Docker, Docker Compose, GitHub Actions.
\end{itemize}

\section{Usine Logicielle, Conteneurisation \& CI/CD}

Pour garantir un déploiement fiable et reproductible sur n'importe quel environnement, le projet s'appuie sur une infrastructure conteneurisée complète.

\subsection{Build Multi-Stage avec Docker}

Le fichier \texttt{Dockerfile} adopte une approche multi-stage optimisant à la fois la sécurité et la légèreté de l'image finale :
\begin{enumerate}
    \item \textbf{Étape de compilation (Builder) :} S'appuie sur l'image \texttt{eclipse-temurin:25-jdk-alpine}. Elle intègre Maven, compile le code source et génère le fichier \texttt{sepa26server.jar}.
    \item \textbf{Étape d'exécution (Runtime) :} S'appuie sur l'image minimale \texttt{eclipse-temurin:25-jre-alpine}. Seul le fichier binaire produit y est copié. L'application est exécutée sous un utilisateur non-privilégié (\texttt{spring:spring}) pour une sécurité renforcée.
\end{enumerate}

L'image produite est baptisée \texttt{sepa26-app:latest}.

\subsection{Orchestration Locale avec Docker Compose}

Le fichier \texttt{docker-compose.yml} orchestre les deux services nécessaires au fonctionnement complet du projet :
\begin{itemize}
    \item \textbf{Service \texttt{db} :} Conteneur MariaDB 11 avec volume persistant (\texttt{mariadb\_data}) et contrôle de santé (\textit{healthcheck}).
    \item \textbf{Service \texttt{app} :} Conteneur applicatif \texttt{sepa26-app} exposé sur le port \texttt{8100}, démarré automatiquement une fois la base de données saine et prête à recevoir des connexions.
\end{itemize}

Le lancement s'effectue en une commande unique :
\begin{center}
    \texttt{docker compose up --build}
\end{center}

\subsection{Gestion des Variables d'Environnement}

La configuration de l'infrastructure est externalisée via des fichiers d'environnement :
\begin{itemize}
    \item \texttt{.env.example} : Modèle versionné décrivant les variables nécessaires (\texttt{SERVER\_PORT}, \texttt{DB\_URL}, \texttt{DB\_USER}, \texttt{DB\_PASSWORD}, \texttt{DB\_ROOT\_PASSWORD}).
    \item \texttt{.env} : Fichier de configuration local, ignoré par Git pour préserver la confidentialité des paramètres.
\end{itemize}

\subsection{Pipeline d'Intégration Continue (GitHub Actions)}

Un workflow GitHub Actions automatisé (\texttt{.github/workflows/ci.yml}) valide l'intégrité du code à chaque \textit{push} et \textit{pull request} :
\begin{enumerate}
    \item Mise en place de l'environnement Java 25 (distribution Temurin) avec cache Maven.
    \item Exécution des suites de tests unitaires et d'intégration (\texttt{mvn clean test}).
    \item Vérification de la construction de l'image Docker multi-stage (\texttt{docker build}).
\end{enumerate}
